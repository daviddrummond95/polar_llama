# Title: Fix Gemma 3n batched generation (shared-KV layers + RoPE offset aliasing) — fixes #1384

## Summary

Batched generation (`mlx_lm.batch_generate`, and `mlx_lm.server`, which
batches internally) produces crashes or silently garbled output for Gemma 3n,
while sequential generation (`mlx_lm.generate`) is fine. This is caused by
two independent bugs in `mlx_lm/models/gemma3n.py::Gemma3nAttention.__call__`,
both only triggered by the batched caches (`BatchKVCache` /
`BatchRotatingKVCache`). Fixes #1384.

## Root cause

**Bug 1 — the loud one (crash).** The KV-shared layers read
`keys, values = cache.state`. `state` is the cache's *serialization* API: the
non-batched caches (`KVCache`, `RotatingKVCache`) return a 2-tuple, but the
batched caches return a 4-tuple `(keys, values, offset, left_padding)` →
`too many values to unpack (expected 2)`.

**Bug 2 — the silent one (garbage), and the actual heart of #1384.** The
attention ropes **keys before** `cache.update_and_fetch(...)` and **queries
after** it, both nominally with the same `offset = cache.offset`:

```python
offset = cache.offset            # captures the cache's offset OBJECT
keys = self.rope(keys, offset=offset)
keys, values = cache.update_and_fetch(keys, values)   # does: self.offset += L
...
queries = self.rope(queries, offset=offset)           # reads offset AFTER +=
```

For the non-batched caches, `cache.offset` is a Python `int` — immutable —
so the captured local keeps the pre-update value, and queries and keys agree.

For the **batched** caches, `cache.offset` is an `mx.array` (one offset per
sequence), and `update_and_fetch` advances it with `self.offset += L`, which
**mutates the same `mx.array` Python object in place**. MLX operations
capture the array's current value at *call* time, so:

- keys are roped with the pre-update offset `p` (correct), but
- queries are roped with the post-update offset `p + L` (wrong, by `L`).

Every layer therefore computes attention with query positions shifted by the
chunk length relative to its keys — `+21` for a 21-token prompt at prefill,
`+1` at every decode step — on **every** layer, not just the KV-shared ones.
The model degenerates into token repetition (`"ItItItIt…"`, `"OkayOkayOkay…"`).

This aliasing is easy to reproduce in isolation:

```python
a = mx.array([0]); b = a; a += 21   # b is now array([21]) — same object!
```

Notably, `gemma3n.py`'s newer sibling architecture, `gemma4_text.py` (whose
batched path already works), guards against exactly this with an
easily-overlooked `offset = mx.array(cache.offset)` snapshot.

Both bugs are invisible in sequential mode, which is why the model "works" in
the common case and the issue understandably suspects only the shared-KV
layers.

## The fix

Mirrors the design `mlx-lm` already uses for `gemma4_text.py`:

1. **Snapshot the RoPE offset** in the concrete (non-shared) branch:

   ```python
   offset = mx.array(cache.offset) if cache is not None else 0
   ```

   `mx.array(...)` copies the pre-update value into a *separate* array, so the
   queries roped after `update_and_fetch` use the same positions as the keys.
   (`self.offset += L` mutates the cache's offset array in place — every alias,
   including the captured local, sees the new value; the snapshot is an
   independent copy that keeps the pre-update positions.)

2. **Thread shared KV through the layer loop instead of reading
   `cache.state`.** Each concrete layer now returns the exact `(keys, values)`
   it attended over (the return value of `update_and_fetch`) plus the offset
   it used. `LanguageModel.__call__` stores these per layer
   (`intermediates`) and hands them to the KV-shared layers via
   `layer_idx_to_cache_idx`. The shared layers consume them directly and
   never touch `cache.state`. This is cache-type-agnostic, so batched caches
   (per-sequence offsets, left padding, rotation) need no special-casing —
   the alignment work was already done by the concrete layer's
   `update_and_fetch` and by the (shared) attention mask.

   As a bonus, this makes the shared layers' query positions *correct*: the
   old code used the post-update `cache.offset` (a `+L` shift baked into the
   sequential path too, just silently absorbed). Empirically that quirk was
   benign in sequential mode — greedy outputs are unchanged token-for-token
   after the fix.

### Why the alignment argument is airtight

A KV-shared layer must attend over exactly the same `(keys, values)` tensor
that its source layer attended over, with queries roped at the same
positions its source layer used — the mask for the layer type is shared and
already consistent with that geometry (left padding, per-sequence offsets,
sliding window, rotation). Passing the source layer's actual tensors and
offset makes this true *by construction*, for every cache implementation,
instead of trying to re-derive the geometry from cache internals via `state`.

## Validation

All runs on Apple Silicon GPU, greedy (`temp=0.0`), chat-templated prompts,
comparing sequential (`stream_generate`) vs batched (`BatchGenerator`, the
same machinery `mlx_lm.server` uses), token-by-token.

**Before the fix** (pristine 0.31.3, with the naive `cache.state[:2]`
band-aid needed just to avoid the crash):

```
seq: 'Paris'                    bat: 'Okay.\n\nItItItItItItIt...'
seq: 'The three primary...'     bat: 'OkayOkayOkayOkayOkay...'
```

**After the fix** (`mlx-community/gemma-3n-E4B-it-lm-4bit`, B=4, 32 tokens):

```
[MATCH]    p0 'Paris'
[MATCH]    p1 'The three primary colors are:\n\n*   **Red**\n*   **Yellow**\n*   **Blue**'
[MATCH]    p2 '2 + 2 = 4'
[NEAR-TIE] p3 diverges at token 31/32: seq ' or' vs bat ' and'
           batched logprobs: ' or' = -0.75, ' and' = -0.75  (exact bf16 tie)
PASS
```

- **3/4 prompts are token-identical** over the full 32-token generation; the
  4th is identical for 31 tokens and flips its final token on an **exact
  logprob tie** (-0.75 vs -0.75 nats in the batched distribution) — expected
  bf16 kernel noise for padded batches, not misalignment.
- **B=1 batched (padding-free) is token-identical to sequential on 4/4
  prompts** — the batched cache path is exact when no cross-sequence padding
  noise exists.
- **Rotation stress:** 640-token generation (sliding window of 512 exceeded,
  `BatchRotatingKVCache` rotates) is **token-identical to sequential for all
  640 tokens**.
- **Control, no regression:** `mlx-community/Qwen2.5-0.5B-Instruct-4bit`
  (full attention, no KV sharing) is 4/4 token-identical batched vs
  sequential, both before and after this change.
- **Sequential unchanged:** greedy sequential outputs are byte-identical to
  pristine `mlx-lm` on all test prompts.
- **`mlx_lm.server` smoke test:** concurrent chat-completion requests for
  Gemma 3n now return correct text (`'Paris\n'`, the correct primary-colors
  list) instead of garbage.

Reproduce with the validator used above (sequential-vs-batched token-parity
check, PASS on token-identical output or a genuine near-tie by logprob gap):

```bash
python benchmarks/validate_1384_fix.py               # patched install
python benchmarks/validate_1384_fix.py --monkeypatch # pristine install + runtime patch
python benchmarks/validate_1384_fix.py --strict      # require exact match, no near-tie allowance
```

## Compatibility

- No public API changes. `Gemma3nAttention.__call__` gains two optional
  keyword arguments (`shared_kv`, `offset`) that are only populated by
  `LanguageModel.__call__` for the KV-shared layers; external callers of the
  attention module directly are unaffected by default.
- Greedy sequential *token* outputs are byte-identical to `main` on all test
  prompts. The offset snapshot also corrects a latent `+L` shared-layer
  query-RoPE error present in sequential mode, so shared-layer *logits* shift
  slightly — a second, quieter correctness fix (greedy decoding is unaffected),
  not a regression.
- Fixes both the crash and the garbage-output cases for batched generation.
